## 1. Согласование технической основы

### Уже согласованные требования

- Первый релиз: Fedora актуального и предыдущего выпуска, KDE Plasma, сеанс Wayland. Поддержка X11 в первый релиз не входит. Формат установки — RPM. Окружение и формат распространения согласованы с пользователем; создание и проверка RPM выполняются на этапе подготовки релиза.
- Настройки и журнал последних файловых операций хранятся в пользовательских папках приложения. История отмены сохраняется после перезапуска; возможность конкретной отмены зависит от сохранности данных и отсутствия конфликтов.
- Расположение выбирается платформенным слоем, формат настроек и журнала общий для ОС:
  - Linux: настройки — `~/.config/papka/`, история — `~/.local/state/papka/`; учитывать переопределения XDG.
  - Windows: настройки — `%APPDATA%\papka\`, история — `%LOCALAPPDATA%\papka\`.
  - macOS: `~/Library/Application Support/papka/`, настройки и история в отдельных подпапках.
- Журнал обновляется по ходу операции для учёта частичного выполнения после сбоя. Согласовано хранение до 100 завершённых действий за последние 30 дней, включая после перезапуска. Формат хранения — версионированный JSON-файл без базы данных; запись через временный файл и атомарную замену.
- История только в текущем сеансе не соответствует требованиям.
- Примеры желаемого интерфейса пользователь предоставит позже. UI — Iced, без HTML и WebView; текущий экран — временная заглушка, не согласованный дизайн.

### Согласованная модель фоновой работы

- `app` владеет состоянием приложения и принимает события последовательно. `ui` отображает состояние и передаёт команды, не выполняя файловый ввод-вывод.
- Два постоянных рабочих потока: один для чтения каталогов, второй для изменяющих файловых операций. Изменяющие операции выполняются последовательно, чтобы собственные копирование, перемещение и отмена не конфликтовали между собой. Изменения извне всё равно требуют проверок.
- Для чтения хранить только последний ожидающий запрос. Каждому переходу присваивать идентификатор; устаревшие результаты не применять. Передавать записи порциями, с ограниченной очередью, чтобы большой каталог не создавал неограниченный буфер.
- Очередь изменяющих команд ограничить 32 заданиями. При заполнении сообщать, что очередь занята, без блокирования UI и молчаливой потери команды. Ограничивать также объём данных задания; списки больших деревьев не загружать целиком заранее.
- События с идентификатором операции: начало, прогресс, запрос решения, завершение. События доставлять через подписку Iced, без опроса таймером. Канал ограниченный; прогресс объединять и передавать не чаще 10 раз в секунду. Запросы решения и итог не отбрасывать. Конкретный адаптер канала выбрать при реализации, не вводя новый runtime заранее.
- Состояния: `Queued`, `Running`, `AwaitingDecision`, `Stopping`, `Finished`. Итог хранить отдельно: успех, ошибка или прерывание, вместе со списком выполненного и невыполненного. Частичное выполнение не считать успехом. Доступность отмены — отдельное свойство результата.
- Прерывание передавать отдельным сигналом, доступным даже при заполненной очереди. Рабочий поток проверяет его между элементами и блоками копирования; уже выполняющийся системный вызов может завершиться позже. `Stopping` не означает, что операция остановлена или отменена.
- При конфликте ждать решения пользователя вне потока UI; сигнал прерывания должен прерывать это ожидание. Следующие изменяющие операции ждут, чтение каталогов продолжает работать. Отмена завершённой операции — новое задание, не сигнал прерывания.
- Завершение окна запрашивает остановку и не объявляет активные операции успешными. Когда будет реализован журнал, подтверждать безопасное завершение только после записи фактического результата; после аварии незавершённые записи требуют сверки с файловой системой, без автоматического повтора разрушительных действий.

Модель согласована с пользователем. Основа реализована в этапе 3: два рабочих потока, очереди, прерывание и подписка Iced. Обработка конфликтов, порционная доставка записей каталога, журнал и ожидание безопасного завершения при закрытии добавляются вместе с соответствующими файловыми операциями.

### Согласованные правила отмены

- Поддерживаемые действия первого релиза: копирование, перемещение, переименование и удаление в корзину. Отмена — отдельная операция, не прерывание выполняющегося действия.
- История сохраняется после перезапуска. Лимиты действуют одновременно: не более 100 завершённых действий и не старше 30 дней с завершения. Групповая операция считается одним действием с результатами отдельных элементов.
- Истечение срока или вытеснение записи убирает возможность отмены через историю papka, но не удаляет пользовательские файлы и содержимое системной корзины. Очистка истории не затрагивает сведения о незавершённых операциях, необходимые для разбора последствий сбоя.
- Доступность записи в истории не гарантирует возможность отмены: изменённые извне данные и конфликты требуют проверки и решения пользователя. Конкретное поведение при конфликтах — следующий пункт плана.

Семантика согласована. В `history::Journal` реализованы открытие журнала после перезапуска, начало записи, контрольные точки частичного выполнения и завершение. Лимиты применяются при открытии, добавлении и завершении записи. Файловые действия и выполнение отмены к журналу пока не подключены.

## 5. Файловые операции и отмена

Реализовано хранилище `history::Journal` (`history.json` и постоянный `history.lock` в переданном каталоге; при подключении использовать `AppDirectories::history`). Один писатель удерживает неблокирующую файловую блокировку. Временный файл создаётся рядом с журналом, синхронизируется и атомарно заменяет его; на Unix синхронизируется каталог. На Linux новые каталоги имеют права 0700, файлы — 0600. Повреждённый/неизвестный формат возвращает ошибку без перезаписи. Сведения о незавершённых действиях не удаляются по сроку и количеству. В записи предусмотрены тип действия, постоянный id, время и двоичные данные восстановления без требования UTF-8; конкретные данные файловых действий ещё не реализованы. Защитные пределы: файл 16 МиБ, контрольная точка 64 КиБ, до 64 незавершённых действий; превышение возвращает ошибку. Ошибка синхронизации после замены требует переоткрытия журнала.

Проверено анализом и успешной Linux-сборкой без предупреждений. Тесты не писались и не запускались агентом реализации. Передача `papka-tester`: сохранение/переоткрытие, границы 100 действий и 30 дней, сохранность незавершённых записей, повреждённый JSON и неизвестная версия, второй писатель, ошибки записи и превышение защитных лимитов. Отдельный `papka-tester` выполнил `cargo test --offline -j 2 --test history`: 15 тестов прошли. Дополнительно прошёл выборочный `disconnected_event_consumer_stops_accepting_reads` после исправления устаревшей подготовки теста, с проверкой отказа обеих очередей. Запуск API при старте UI, восстановление после аварии и фактическая отмена пока не подключены; аварийное отключение питания, ошибка fsync после замены, Windows/macOS и GUI не проверены.

## 7. Независимое тестирование

- [ ] Проверять файловые операции только во временных каталогах с тестовыми данными.

- [ ] Измерить производительность и потребление ресурсов в согласованной среде.

Результат: отчёт о выполненных проверках, дефектах и фактических ограничениях. Пока отдельный агент не выполнил этап, тестирование остаётся незавершённым.
