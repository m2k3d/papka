### Связанные цветовые гармонии по механике Zen — 12 ноября 2026

Прямой запрос пользователя заменяет прежнее решение про независимые пространственные схемы. Это один шаг реализации редактора в рамках существующего Rust / Iced, без новых зависимостей и платформенных изменений.

- [x] Изучен официальный исходник [ZenGradientGenerator.mjs](https://github.com/zen-browser/desktop/blob/dev/src/zen/spaces/ZenGradientGenerator.mjs): `colorHarmonies`, `calculateCompliments`, `getColorFromPosition`, обработчики добавления / удаления / движения. В Zen используется цифровой HSL-круг: угол — оттенок, радиус — светлота, насыщенность при обычном движении 90–100%. Это не отдельная модель RYB Иттена. Реализация на Rust написана самостоятельно; код JS и ресурсы Zen не включались.
- [x] Для двух точек доступны Complementary (180°), Analogous (−50°), Custom; для трёх — Split complementary (150° / 210°), Analogous (±50°), Triadic (120° / 240°), Custom. Для одной — Single. Кнопка показывает текущую схему и перебирает только подходящие варианты.
- [x] В связанных схемах перетаскивание любой точки пересчитывает все цвета и позиции на одном радиусе с фиксированными углами. Жест не переводит схему в Custom. В Custom движение независимо. Добавление / удаление подбирает совместимую схему, пара / тройка Analogous сохраняет семейство.
- [x] Цветовой круг рисуется из той же формулы HSL, что применяется к точкам. Его геометрия кешируется независимо от цветов; отдельно рисуются соединения и точки. Круг вписан без искажения пропорций, движение ограничено окружностью. Щелчок на свободном месте круга перемещает выбранную точку. Захват края точки сохраняет смещение курсора, потеря фокуса завершает жест.
- [x] Под кругом расположен отдельный предпросмотр смешанного фона; нумерованные переключатели оставлены для перекрытых точек. HEX применяется точно и пересчитывает связанные оттенки с той же насыщенностью / светлотой; положение определяется оттенком и светлотой. Последующее движение использует обычную формулу круга с высокой насыщенностью, как в Zen.
- [x] В настройки добавлено необязательное `palette_harmony` с именованными значениями. Старый `palette_combination` сохранён для совместимости; отсутствие нового поля открывает старую палитру как Custom, без изменения RGB и старого фона. Перевод позиций в координаты круга происходит при редактировании. Reset восстанавливает исходную триаду и все параметры палитры; тема и каталог не меняются.
- [x] Проверены логика, маршрутизация событий и компиляция: `cargo check --offline -j 2` и нетестовая `cargo build --offline -j 2`, без предупреждений. Бинарник `build/debug/papka` обновлён. Тесты не изменялись и не запускались.
- [ ] Отдельному тестировщику: проверить углы и общий радиус во всех схемах, движение каждой точки / через границу 0° / через центр / вне круга, переходы 1↔2↔3 и выбор скрытой точки; HEX и серые / чёрные / белые цвета; Custom и возврат к гармонии; загрузку старого JSON без поля и нового JSON с каждой схемой, повторное открытие и полный Reset. Актуализировать прежние ожидания произвольных схем и геометрию круга в Canvas-проверках, сохранив регрессию потери фокуса. Проверить сохранение страницы и выделения при всех изменениях оформления.
- [ ] Нативное окно, Wayland / DPI, визуальное качество круга и градиента, плавность и ресурсы не проверены. Наличие кеша не считается измерением производительности.

Не выполнены GUI-проверка на Fedora/KDE/Wayland, независимые тесты, измерения и подготовка релиза.

### Согласованная модель фоновой работы

- `app` владеет состоянием приложения и принимает события последовательно. `ui` отображает состояние и передаёт команды, не выполняя файловый ввод-вывод.
- Два постоянных рабочих потока: один для чтения каталогов, второй для изменяющих файловых операций. Изменяющие операции выполняются последовательно, чтобы собственные копирование, перемещение и отмена не конфликтовали между собой. Изменения извне всё равно требуют проверок.
- Для чтения хранить только последний ожидающий запрос. Каждому переходу присваивать идентификатор; устаревшие результаты не применять. Передавать записи порциями, с ограниченной очередью, чтобы большой каталог не создавал неограниченный буфер.
- Очередь изменяющих команд ограничить 32 заданиями. При заполнении сообщать, что очередь занята, без блокирования UI и молчаливой потери команды. Ограничивать также объём данных задания; списки больших деревьев не загружать целиком заранее.
- События с идентификатором операции: начало, прогресс, запрос решения, завершение. События доставлять через подписку Iced, без опроса таймером. Канал ограниченный; прогресс объединять и передавать не чаще 10 раз в секунду. Запросы решения и итог не отбрасывать. Конкретный адаптер канала выбрать при реализации, не вводя новый runtime заранее.
- Состояния: `Queued`, `Running`, `AwaitingDecision`, `Stopping`, `Finished`. Итог хранить отдельно: успех, ошибка или прерывание, вместе со списком выполненного и невыполненного. Частичное выполнение не считать успехом. Доступность отмены — отдельное свойство результата.
- Прерывание передавать отдельным сигналом, доступным даже при заполненной очереди. Рабочий поток проверяет его между элементами и блоками копирования; уже выполняющийся системный вызов может завершиться позже. `Stopping` не означает, что операция остановлена или отменена.
- При конфликте ждать решения пользователя вне потока UI; сигнал прерывания должен прерывать это ожидание. Следующие изменяющие операции ждут, чтение каталогов продолжает работать. Отмена завершённой операции — новое задание, не сигнал прерывания.
- Завершение окна запрашивает остановку и не объявляет активные операции успешными. Когда будет реализован журнал, подтверждать безопасное завершение только после записи фактического результата; после аварии незавершённые записи требуют сверки с файловой системой, без автоматического повтора разрушительных действий.

Модель согласована с пользователем. Основа реализована в этапе 3: два рабочих потока, очереди, прерывание и подписка Iced. Обработка конфликтов, порционная доставка записей каталога (до 256 записей в событии), журнал и ожидание завершения при закрытии теперь реализованы; независимая проверка ещё предстоит.

### Согласованные правила отмены

- Поддерживаемые действия первого релиза: копирование, перемещение, переименование и удаление в корзину. Отмена — отдельная операция, не прерывание выполняющегося действия.
- История сохраняется после перезапуска. Лимиты действуют одновременно: не более 100 завершённых действий и не старше 30 дней с завершения. Групповая операция считается одним действием с результатами отдельных элементов.
- Истечение срока или вытеснение записи убирает возможность отмены через историю papka, но не удаляет пользовательские файлы и содержимое системной корзины. Очистка истории не затрагивает сведения о незавершённых операциях, необходимые для разбора последствий сбоя.
- Доступность записи в истории не гарантирует возможность отмены: изменённые извне данные и конфликты требуют проверки и решения пользователя. Конкретное поведение при конфликтах — следующий пункт плана.

Семантика согласована. В `history::Journal` реализованы открытие журнала после перезапуска, начало записи, контрольные точки частичного выполнения и завершение. Лимиты применяются при открытии, добавлении и завершении записи. Файловые действия и выполнение отмены подключены к журналу; новые сценарии ещё ожидают независимого тестирования.

## 5. Файловые операции и отмена

Реализовано хранилище `history::Journal` (`history.json` и постоянный `history.lock` в переданном каталоге; при подключении использовать `AppDirectories::history`). Один писатель удерживает неблокирующую файловую блокировку. Временный файл создаётся рядом с журналом, синхронизируется и атомарно заменяет его; на Unix синхронизируется каталог. На Linux новые каталоги имеют права 0700, файлы — 0600. Повреждённый/неизвестный формат возвращает ошибку без перезаписи. Сведения о незавершённых действиях не удаляются по сроку и количеству. В записи предусмотрены тип действия, постоянный id, время и двоичные данные восстановления без требования UTF-8; конкретные данные файловых действий ещё не реализованы. Защитные пределы: файл 16 МиБ, контрольная точка 64 КиБ, до 64 незавершённых действий; превышение возвращает ошибку. Ошибка синхронизации после замены требует переоткрытия журнала.

Проверено анализом и успешной Linux-сборкой без предупреждений. Тесты не писались и не запускались агентом реализации. Передача `papka-tester`: сохранение/переоткрытие, границы 100 действий и 30 дней, сохранность незавершённых записей, повреждённый JSON и неизвестная версия, второй писатель, ошибки записи и превышение защитных лимитов. Отдельный `papka-tester` выполнил `cargo test --offline -j 2 --test history`: 15 тестов прошли. Дополнительно прошёл выборочный `disconnected_event_consumer_stops_accepting_reads` после исправления устаревшей подготовки теста, с проверкой отказа обеих очередей. Связанные требования: текущий запрос про изменение только оформления и требования AGENTS.md к отзывчивости UI. Исправление передано на этап реализации, падающий тест сохранён.

Не проверено: визуальная компоновка / плавность, малые окна и масштабирование, фактический правый клик и двойной щелчок, перенос сетки и длинных имён, полная маршрутизация ввода модального редактора и сохранение во время быстрого движения ползунка. Приватные `ui::Message` / `update` не доступны integration-тестам без изменения реализации; HEX, ограничение количества цветов `clamp(1,3)` и блокировка необработанных горячих клавиш изучены только анализом кода. Платформенные интеграции и файловые операции не запускались: они не изменялись в этом шаге. Native GUI automation недоступна. Независимая проверка UI остаётся частичной, выпуск не подтверждён.

Тестовые сборки создавались исключительно в `/tmp/papka-ui-tester-20261111`, после проверки удалены. В проектном `build/` по-прежнему один файл `build/debug/papka`.
